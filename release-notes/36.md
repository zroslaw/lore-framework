# Release Notes — Version 36

## Summary

Version 36 makes Lore easier to navigate and cheaper to load: a small v1 frontmatter schema now
defines context, recursive areas, and leaf topics; deterministic maps expose structure and
coverage; merge adopts the format gradually; and `/lr:groom` performs bounded semantic cleanup.

## Clear Plugin Cache

Refresh the Lore plugin and start a new session before using v36. This release adds `/lr:groom`,
changes boot and merge procedures, and updates the bundled `lr-core` script.

1. **Claude Code:** `rm -rf ~/.claude/plugins/cache/lore-framework/` (targeted), or
   `rm -rf ~/.claude/plugins/cache/` (broader fallback).
2. **Cursor:** run `bash /path/to/lore-framework/scripts/cursor-refresh-plugin`.
3. **Codex:** run `bash /path/to/lore-framework/scripts/codex-refresh-plugin`.

## What Changed

- Lore v1 defines one fixed context, recursive knowledge areas, and focused leaf topics using four
  bounded frontmatter fields: `lore`, `type`, `summary`, and `parent`.
- `lr-core lore-map` emits compact boot navigation or a detailed validated taxonomy with token,
  link, date, coverage, and compatibility data.
- `lr-core lore-workset` selects a deterministic ≤30K-token grooming workset and read-only halo,
  with omission counts and SHA-256 review snapshots.
- The stable `scripts/lr-core` command is now a thin compatibility wrapper over focused
  standard-library modules in `scripts/lr_core/`. Manual fallbacks read only the relevant
  preflight or scan module instead of loading the entire graph, map, and grooming implementation.
- Boot receives the compact map and ends with one standard three-line report showing Lore file
  count, total Lore size, taxonomy coverage, and a total footprint split into Lore context, map,
  role, and system prompts. Token figures are ceiling-rounded to thousands for display. Attach
  reports the guest's Lore and added role/context/map footprint without re-counting the host's
  already-loaded system prompts. A map failure reports unavailable statistics and falls back to
  normal Lore search without blocking boot or attach.
- Merge writes v1 metadata on new files and may lazily migrate only clearly understood touched
  files plus the minimum existing ancestor chain.
- Explicit and boot-time framework updates now commit only update-owned repo paths and try to push
  them to the existing upstream. Dirty update targets, staged user work, unrelated unpublished
  commits, missing upstreams, and push failures remain visible; publication never force-pushes.
- `/lr:groom [scope] [--dry-run] [--all]` removes AI slop, improves taxonomy and summaries, and
  supports explicit whole-Lore conversion behind a proposal and approval checkpoint.
- New agents start with a v1 context. Existing agents are not rewritten by the update.

## Compatibility

Legacy, mixed, and complete agents all remain usable. Coverage reports the exact file and estimated
token share represented by the map. Unsupported future-version files are visible but read-only.
A valid v1 child can temporarily point to an incompatible legacy root and is reported as
`unreachable_v1` rather than corrupted.

Invalid UTF-8 no longer disables the map. Coverage emits no per-file corruption list, only the
affected count. Those files remain outside taxonomy, reference-source scanning, and grooming until
repaired.

Migration 36 intentionally writes no agent files. Normal merge raises coverage gradually; explicit
grooming handles broader conversion when the user wants it.

## Safety

Grooming uses bounded contexts, read-only halos, source hashes, destination no-clobber checks,
complete formal and conservative inbound-reference scans before path changes, and post-write map
validation. A nonzero invalid-UTF-8 count blocks structural path changes and Whole-Lore mode because
the scan cannot then be complete. Whole-Lore never writes before approval.

Framework-update publication stages explicit update-owned paths only. It does not absorb unrelated
dirty work, guess an upstream, or force-push; a commit or push failure never rolls back a valid
migration stamp and is reported for retry.

## Validation

- The explicit non-real-engine development suite passes all 315 tests. No module below
  `tests/lifecycle/` was invoked. The focused Lore v1 module passes all 46 contracts; the final
  `lr-core` plus Lore v1 subset passes 109 tests.
- Generated boot, detailed, and workset YAML parses successfully against the real 220-file Lore
  Architect corpus. The compact boot view is 857 bytes (215 estimated tokens), and reports a
  22,223-token estimated total boot footprint under the codex engine profile: 10,798 Lore-context
  tokens, 215 map tokens, 3,685 role tokens, and 7,525 system-prompt tokens. The system-prompt
  component is engine-specific; the claude profile measures 6,234 on the same tree. The selected workset is 29,946 estimated tokens
  against a 30,000-token budget.
- Before the final review fixes and boot-report addition, all five Lore v1 lifecycle scenarios
  passed on Cursor `composer-2.5`: boot map, merge adoption, dry-run immutability,
  knowledge-preserving slop removal, and whole-Lore approval gating.
- That earlier Cursor run is historical smoke evidence, not certification of the corrected tree,
  because an older global Cursor cache was present and identity preflight was deliberately
  bypassed. Real-engine lifecycle tests were deliberately excluded from this local release-candidate
  preparation at the user's direction; run them or record an explicit waiver before the eventual
  push.
