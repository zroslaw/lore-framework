# v44 — Every skill says what it is about to do, and shortcuts survive a clone

## Summary

Invoking a Lore skill used to begin with silence. `/lr:workspace-init` and `/lr:workspace-status`
would start scanning, `/lr:boot` would spend a minute pulling over the network, and nothing on
screen explained what was happening or why. That is legible to whoever wrote the skill and opaque to
everyone else — exactly backwards for someone trying the framework for the first time.

From v44, **all 33 skills print a short announcement before they start working**: what will happen,
why, and what to expect, in three or four plain sentences. Each is written for that specific
command, names the framework concepts it touches (lore, roles, lore agent repos, subagents) rather
than assuming them, and bolds the one thing a newcomer is most likely to get wrong — usually what
the skill does to their files, sometimes a scope boundary or a distinction from a neighbouring
skill.

The announcements double as onboarding. Reading them in sequence teaches the framework's vocabulary
without a separate tutorial.

**Migration required:** yes — `migrations/44.md`, for the second change below.

## Clear Plugin Cache

This release changes every skill's procedure, so the existing plugin cache must be refreshed before
the announcements appear.

1. **Claude Code:** `rm -rf ~/.claude/plugins/cache/lore-framework/` (targeted; preserves other
   plugins' caches), or `rm -rf ~/.claude/plugins/cache/` (broader fallback).
2. **Cursor:** run `bash /path/to/lore-framework/scripts/cursor-refresh-plugin`.
3. **Codex:** run `bash /path/to/lore-framework/scripts/codex-refresh-plugin`.
4. Exit the current session and start a new one.

If you skip this step, skills will continue running silently. See `docs/doctor-stale-plugin-cache.md`
for diagnosis.

## What Changed

### The announcement convention

`docs/conventions.md` gains **§ Skill Purpose Announcement**, the authoring rule for new and changed
skills. Its load-bearing choices:

- The text is **authored per skill and lives in that skill's own doc**. There is no shared template
  to point at — the value is in prose written for one specific command, and a common file would only
  add a read at invocation time while inviting drift.
- It sits in a `## Step 0 — Announce` section before the first procedural step. Location decides
  whether an instruction runs, and Step 0 is the one position a paged doc cannot skip past.
- Framework concepts, never internals: "I pull its lore agent repo," not the script that does it.
- `<placeholder>` slots carry a standing instruction to substitute them, because models print
  examples verbatim.

### Per-skill announcements

All 33 skills. Three carry their Step 0 outside `docs/`: `list-agents` and `list-repos` have no
companion doc and carry it in `SKILL.md`; the two `df-*` skills carry it under `df/`. One doc,
`register-repo.md`, backs four skills, so its Step 0 branches on the invoked operation.

### Terminology: "lore agent repo"

Announcements say **lore agent repo**, not "repo", wherever they mean a git repo holding agents. A
workspace commonly holds both those and the ordinary source repos the agents work on, and the
distinction matters most to a newcomer who has just added their application's repo alongside.

### Boot step renumbering

`agent-boot.md`'s `## Step 0 — Framework root` becomes `## Framework root`, freeing Step 0 for the
announcement. Its own text already described it as running "before the numbered steps," so it only
sheds a number it was borrowing. **Steps 1–5 keep their numbers**, so the 16 external references to
them across `conventions.md`, `auto-pull.md`, `spawn-teammate.md`, `check.md`, `version-check.md`,
`teammate-conventions.md`, and the three engine profiles all still resolve.

The three engine profiles cited boot's "Step 0" for framework-root self-location; they now name the
section instead of a number, which is stable across future renumbering.

Two other docs had a colliding `### Step 0` with no references anywhere:
`workspace-init.md`'s becomes `### Context`, `process-merge.md`'s becomes `### Refresh the Repo`.

## Committed shortcuts now carry relative paths

A second, independent fix ships in v44.

Generated per-agent shortcuts embedded an **absolute** agent directory. Shortcuts are committed —
`.claude/commands/`, `.codex/skills/`, and `.cursor/skills/` all travel with the workspace repo — so
every one of them published local configuration as if it were shared configuration. Two things
followed, and the second is the one that went unnoticed:

- A teammate cloning the workspace got a shortcut pointing at a directory on **your** machine.
- `workspace-status` matches registered shortcuts by their embedded target, so a cloned workspace
  reported **every agent as unregistered** — the shortcut sitting in git, and the finding saying it
  was missing. A wrong path does not merely fail; it makes a diagnostic lie about a different thing.

This lands one version after v43 made a cloned workspace arrive with `lr` already configured. That
premise only holds if what arrives also works.

**What changed:**

- `conventions.md` gains **§ Committed Artifacts Carry Relative Paths** — any path written into a
  committed file is relative to its repo root. Runtime values (a resolved `<framework-root>`, a
  `--agent-dir` argument) are explicitly outside it.
- New placeholder **`<agent-dir-rel>`**, distinct from `<agent-dir>`. The two forms were one word
  doing two jobs: an absolute runtime argument and a committed path. The three engine profiles and
  `register-repo.md` now emit the relative form.
- `shortcut_targets()` resolves a relative target against the workspace and still accepts an
  absolute one, so a workspace mid-migration reports correctly either way. A relative target in the
  user-global `~/.codex/skills/` is skipped rather than guessed at — it belongs to no particular
  workspace.
- `/lr:check` #18 flags an absolute `from` target as a legacy artifact.
- **`migrations/44.md`** regenerates affected shortcuts. It regenerates rather than substituting the
  path, because a shortcut old enough to carry an absolute agent directory usually carries other
  retired forms too. Run **`/lr:workspace-push`** afterwards — the rewrite lands in the workspace
  repo, which the update process's own commit does not cover.
- `preflight --agent-dir` now accepts a workspace-relative directory as well as an absolute one, so
  the executor passes a shortcut's target through unchanged. It is resolved by searching upward from
  the session directory for the agent's `role.md`, which makes the shortcut work from a
  subdirectory or a worktree rather than only from the workspace root.

## Creating an agent now registers it

`/lr:create-agent` used to stop after writing `role.md`, `lore-context.md`, `lore/`, and `workdir/`,
then *offer* `/lr:register-agent` as a follow-up. Registration is what adds an agent to the workspace
memory file's `## Agents` section — the "what can I boot here" list a teammate reads on arrival — so
an agent created and not registered was bootable by name and invisible to everyone else. It also
landed straight into `workspace-status` finding **S11**, meaning the framework's own skill produced
the state its own diagnostic reports.

From v44, `create-agent` runs the Register Agent procedure itself. **This means creating an agent now
writes outside the agent's own directory** — an engine-native shortcut, the `## Agents` section of
`AGENTS.md`, and the `@AGENTS.md` import line in `CLAUDE.md`, all in the *workspace* repo. They are
left uncommitted; `/lr:workspace-push` publishes them. If the workspace has no `AGENTS.md`, or one
without an `## Agents` heading, nothing is synthesized: registration still succeeds and the report
names `/lr:workspace-init`.

`create-agent` also stops rather than guessing when the workspace holds **no lore agent repo** — the
case a reader following the README's opening example hits — and offers `/lr:create-repo` instead of
scaffolding an agent directory that no discovery could ever find.

## Verification

Gate dispositions for this release, named explicitly:

- **Deterministic tests — passed.** 540 tests across 15 modules in `lore-framework-dev/tests/`
  (the dev repo, not this one — `docs/conventions.md` § Dev-Only Artifacts), run against this tree.
- **`/lr:check` — passed**, after fixing the one error it reported.
- **Dogfooding — passed.** The changed procedures were run against this workspace.
- **Lifecycle suite, Claude Code — partial.** 8 of 9 modules pass. The one failure v44 caused was
  fixed and re-verified; the three remaining reds are pre-existing flakes with failing history on
  the pre-v44 checkout (`test_05`, `test_08`, `test_12`).
- **Lifecycle suite, Codex and Cursor — did not run.** Both refused on the plugin-identity gate,
  which needs local install changes to clear. Not a waiver of the gate's value — a cost and
  environment decision, recorded so it is not mistaken for a pass.
- **`/code-review` — four rounds, converged.** Round 4's own fixes are themselves unreviewed.

**What remains untested:** real-engine execution of the changed procedures on **Codex and Cursor**.
v44 touches files both engines read — `scripts/lr_core/preflight.py`, `workspace_scan.py`, both
engine profiles, and the Cursor skill mirrors — so their behavior after this release rests on
review and on the deterministic suite, not on execution evidence. Claude Code is the only engine
with an execution gate behind this version.

## Known Limits

- **`being.md` and `create-agent.md` step 8 disagree about who decides registration for a Being.**
  `create-agent` now registers what it creates, but the Being path documents an opt-out. Creating a
  Being may therefore follow either reading depending on which doc the executor pages. Known bug,
  shipped knowingly; it affects Beings only, which are BETA.
- No `/lr:check` item verifies `## Step 0 — Announce` is present. The convention has 33+ sites and
  no mechanical enforcement, so it can drift silently between releases.
- `preflight --agent-dir`'s upward search is covered by hand-verification across five invocation
  shapes, not by a test.
- The lifecycle runner (`run_matrix.py`) exits 0 both when the suite refuses to run and when module
  runs fail, so its exit code is not a verdict — read the summary block.
