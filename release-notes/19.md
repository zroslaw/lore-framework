# Release Notes — Version 19

## Summary

Version 19 makes the framework **multi-engine**: the same team-shared agent repo can now be driven
by **Codex** as well as **Claude Code**. The knowledge substrate was always engine-agnostic (plain
markdown, git, `lore-repo.md`, `role.md`, `lore/`, `lore-context.md`); what changes here is the thin
adapter layer that let the *procedures* assume Claude Code. This ships as a new `docs/engines/`
engine-profile convention, a boot-time engine-selection step, and the replacement of the
Claude-only `${CLAUDE_PLUGIN_ROOT}` with a neutral, self-located `<framework-root>` term.

It also lands three user-invoked **style skills** — `/lr:plain-language`, `/lr:dialogue`,
`/lr:follow-me` — and a boot-robustness fix so a deferred version upgrade is never mistaken for a
boot failure.

The Codex path (boot, recall, merge, finalize) is validated end-to-end on real `codex exec`. Some
plugin subsystems remain Claude-first for now — see **Scope** below.

## Clear Plugin Cache

This release rewrites **every `SKILL.md`** (self-location line) and many `docs/` procedures, adds
`docs/engines/`, and bumps the plugin manifest `1.18.0` → `1.19.0`, so the existing plugin cache
must be refreshed before Claude Code will load the new versions.

After upgrading:

1. `rm -rf ~/.claude/plugins/cache/lore-framework/` (targeted; preserves other plugins' caches), or
   `rm -rf ~/.claude/plugins/cache/` (broader fallback), or run the workspace's
   `./clear_plugin_cache.sh` if present.
2. Exit your current Claude Code session and start a new one.

If you skip this step, the prior version's catalog loads until the cache refreshes. See
`docs/doctor-stale-plugin-cache.md` for diagnosis, or run `/lr:doctor`.

## Status

Stable on Claude Code (no behavior change; the `<framework-root>` term resolves to the same paths).
**BETA on Codex** for the core lifecycle. Release-notes-only — **no migration required**: all
changes are inside the plugin; nothing on existing agent repos changes, and `lore-repo.md` version
stamps advance the next time each agent boots.

## What's New

### The `docs/engines/` engine-profile convention

One profile per engine — `docs/engines/claude.md` (the reference) and `docs/engines/codex.md` —
each filling the **same five bindings**: framework-root, invocation-syntax, subagent-spawn,
memory-file, runtime-bounding, plus capability gates. Only the values differ. Shared procedure docs
stay engine-agnostic and carry a one-line **Engine note** at each engine-specific site (fan-out,
memory-file, runtime-bounding) pointing at the active profile's override, which wins at execution
time.

### Boot Step-0 — framework root & engine selection

`agent-boot.md` gains a Step 0 that runs before the numbered steps: (1) resolve `<framework-root>`
by self-location (the directory containing `VERSION`), and (2) infer the engine — non-empty
`${CLAUDE_PLUGIN_ROOT}` → Claude; a `~/.codex/` root → Codex; else default Claude — then read that
engine's profile and hold its bindings as standing session context.

### `<framework-root>` replaces `${CLAUDE_PLUGIN_ROOT}`

The Claude-only variable is replaced everywhere in `docs/` and `skills/` by the neutral defined term
`<framework-root>`, resolved by a one-line self-location rule injected at the top of every
`SKILL.md`. On Claude Code this resolves to exactly the same path as before; on engines where the
env var is empty (Codex), self-location is what makes the framework locatable at all.

### Codex profile highlights (`docs/engines/codex.md`)

- **Subagent fan-out** (merge / recall / consult) via Codex's native `spawn_agent` / `wait_agent`,
  with the host reading the procedure and passing steps inline to each worker.
- **Memory file** is `AGENTS.md` (not `CLAUDE.md`); `/lr:init` writes whichever the profile names.
- **Sandbox git handling**: Codex's `workspace-write` sandbox blocks `.git/` writes, so `auto-pull`
  degrades cleanly and `finalize`'s commit either runs with `.git` made writable or leaves the
  merged changes for the user to commit by hand — never treated as a merge failure.
- **Capability gate**: the `ps`-based teammate probe is sandbox-blocked and degrades to a normal
  host session.

### Style skills

Three composable, user-invoked skills that change how the agent communicates — sentence-level
(`/lr:plain-language`), turn-level (`/lr:dialogue`), and thinking-direction (`/lr:follow-me`). Thin
pointers to `docs/`, re-asserted by invoking their trigger; not boot-loaded.

### Boot robustness — deferred upgrade is not a boot failure

`version-check.md` and `agent-boot.md` step 3 now state, adjacent to each alarming deferral message,
that a deferred or failed upgrade is **not** a boot failure — the agent still loads in degraded
mode. (Surfaced by running the lifecycle harness on a weak model, which read the scary message and
stopped instead of continuing.)

## Scope

Ported and validated on Codex: **boot, recall, merge, finalize** — the core lifecycle. Deferred,
Claude-first for now: the **`lr-wait` MCP server**, the **DF / AIQA** module, and `migrations/*`
still reference `${CLAUDE_PLUGIN_ROOT}` and target Claude Code. Cursor `--plugin-dir` parity is
expected but unconfirmed. These are follow-ups, not regressions — the Claude Code path is unchanged.

## Conventions established

- **`docs/engines/<engine>.md` engine profiles** — five bindings + capability gates; profile wins
  on conflict with a shared procedure doc.
- **Boot Step-0** — resolve `<framework-root>` by self-location, then select the engine profile.
- **Engine-note pattern** — shared docs describe the Claude mechanism and point at the profile
  override at each engine-specific site, rather than forking the doc per engine.
