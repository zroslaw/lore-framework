# Release Notes -- Version 30

## Summary

Version 30 adds **`/lr:trilens-loop`** — review a set of changes from three independent
perspectives, triage the findings, fix what matters, and repeat until the changes come back clean.
The three reviewers are subagents, so they do not carry the authoring session's bias toward its own
work.

It also corrects two engine profiles: Cursor's `subagent-spawn` binding (stale since Cursor shipped
subagents in 2.4) and Claude Code's (which never documented `fork` or the named-teammate
non-return trap).

## Clear Plugin Cache

This release **adds** a bundled skill (`skills/trilens-loop/SKILL.md`) and its SKILL-referenced doc
(`docs/trilens-loop.md`), adds the generated Cursor wrapper
(`.cursor-skills/lr-trilens-loop/SKILL.md`), and **modifies** `docs/engines/cursor.md` and
`docs/engines/claude.md`. Refresh before expecting `/lr:trilens-loop` to appear in an installed
plugin copy.

Repo migration required: **no** — the skill writes no files into agent repos; existing agent repos
auto-stamp on next boot.

After upgrading:

1. **Claude Code:** `rm -rf ~/.claude/plugins/cache/lore-framework/` (targeted), or
   `rm -rf ~/.claude/plugins/cache/` (broader fallback). Exit the current session and start a new one.
2. **Cursor:** run `bash /path/to/lore-framework/scripts/cursor-refresh-plugin`, then start a fresh
   `cursor-agent --plugin-dir /path/to/lore-framework` session.
3. **Codex:** `codex plugin marketplace upgrade lore-framework` (or `codex plugin add lr@lore-framework`),
   then start a fresh Codex session.

## What's New

### `/lr:trilens-loop`

Three reviewers, one round at a time, until nothing worth fixing comes back.

- **Default scope is the current session's changes** — the files this session touched, unioned with
  the uncommitted working-tree changes in the repos they live in. Not a git range. An empty scope
  stops and reports rather than spawning reviewers over nothing.
- **The host session picks the three lenses** per invocation, from the change itself. A lens is a way
  of looking, not a place to look; lenses must be mutually exclusive, and each brief tells its
  reviewer what the other two own. The three lenses stay fixed for the whole loop.
- **Reviewers are independent subagents.** They did not author the changes, they start cold, and they
  are read-only — they report, the host fixes. Context-inheriting forks are forbidden: a fork carries
  the very bias the skill exists to remove.
- **Reviewers default to a regular model tier**, not a flagship one — sonnet on Claude Code, gpt-4.5
  on Codex, composer-2.5 on Cursor. Budget belongs in rounds and independence, not model size.
- **Triage is the host's call.** Every `BLOCKER`/`HIGH` is verified against the actual file before
  being acted on; findings may legitimately be declined with a reason. The ledger has three states:
  `APPLIED`, `DECLINED`, and `ACCEPTED (not applied — report-only)`.
- **The loop is the feature.** Each later round gets fresh reviewers, briefed with an
  **APPLIED / DECLINED (+reason)** ledger of that lens's own prior findings, so settled items stay
  settled instead of resurfacing every round.
- **Termination has three guards** — a round cap (default 3), a reviewer-gated stop (the loop may not
  end while any reviewer's latest verdict is `BLOCK` unless the host says out loud that it is
  overriding), and a rule that a silent round is not a clean round: at least one reviewer must have
  actually returned before a round counts as clean.
- **One free-text argument, no flags** — `/lr:trilens-loop only one round, no fixes`,
  `/lr:trilens-loop use security, performance and API compatibility as the lenses`. Free text
  outranks every default including the rails; when it switches a rail off, the skill says so in its
  output rather than complying silently, and a user-requested self-review is labelled as a
  self-review rather than a trilens review.

The skill is **change-scoped**, which is what separates it from its state-scoped siblings:
`/lr:check` checks a domain's content consistency, `/lr:doctor` diagnoses runtime ailments. It is not
part of finalization — it never writes lore, never reflects, never merges, never commits.

### Engine profiles corrected

**Cursor.** `docs/engines/cursor.md` carried a conservative binding stating that no Cursor-native
in-session subagent mechanism was relied on. That was epistemic caution rather than a discovered
limitation, and it had gone stale: Cursor shipped subagents in **2.4** (2026-01-22; editor, CLI and
Cloud Agents), dispatched via a `Task` tool, with async subagents and the nesting rule following in
2.5.

The binding now keeps serial host-side execution as the validated default for the procedures that
already pass that way (recall, consult, attach, merge, conflict resolution), and carves out one
exception: procedures where **subagent independence is the semantics rather than an optimization**
use `Task`. `trilens-loop` is the only such procedure today, and that is the reason the carve-out
exists — serial host-side execution of a bias-removal review is not a slower version of the
procedure, it is an invalid one.

A new § Native subagents section separates what Cursor documents from what this framework has
actually validated, and flags the load-bearing unknown: whether `Task` accepts a free-text brief or
only dispatches pre-defined agent files by name. Procedures using `Task` on Cursor handle the
name-only case by writing throwaway `readonly` definitions under `.cursor/agents/` and deleting them
afterwards.

**Claude Code.** `docs/engines/claude.md`'s `subagent-spawn` binding now names all three subagent
types and their two traps: `fork` inherits the caller's context (unusable where independence is
required), and passing a `name` makes the call an Agent-Teams teammate, which **does not auto-return
its report to the caller**. Both traps were previously undocumented in the profile and both are easy
to hit.

## Verification

- Lifecycle scenarios 28–29 (`tests/lifecycle/test_trilens_loop.py`, dev repo) drive the skill
  end-to-end on a real engine: a planted uncommitted lore topic carrying a dangling cross-reference
  and a contradiction against committed fixture lore is reviewed in a single round. Scenario 28
  allows fixes and asserts the target file was edited; scenario 29 amends the flow to report-only and
  asserts the file is byte-identical afterwards — a filesystem check of the free-text rail rather
  than a self-report. Both assert three distinct lenses were chosen.
- **Full pass: 3/3 engines green** — claude/haiku, codex/gpt-5.4-mini, cursor/composer-2.5. The
  Cursor run is the most informative: on the weakest tier it produced the scope union, disclosed the
  round-cap override, disclosed the Cursor path as documented-but-unvalidated per the engine profile,
  chose three real lenses, found both planted defects, and used the report-only ledger state.
- **Known flakiness, shipped as-is:** on repeat runs, `codex` at its cheapest tier
  (`gpt-5.4-mini`) sometimes returns `FINDINGS: none` on scenario 28 over a file with two planted
  defects — i.e. it declares a silent round clean instead of following the retry-then-report rule.
  Observed 1 failure in 2 repeat runs with an unchanged doc, so it reads as weak-model variance
  rather than a procedure defect; the same doc passes on the other engines and on codex's other
  scenario. The rule is correct but not binding enough for that tier. Not fixed in this release.
- The skill was also run against its own changes during development: four rounds
  (14 → 6 → 1 → 0 findings), 20 findings applied and 1 declined, converging to a clean round. That
  loop caught a self-contradiction between the free-text rule and the no-self-review rule, the
  named-teammate trap (hit live), an unsourced factual claim about Cursor's changelog, a
  fix-the-fixes miss across three files, and a lifecycle scenario-number collision.
