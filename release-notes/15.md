# Release Notes — Version 15

## Summary

Version 15 fixes four real-use procedural failures, all surfaced in a single live debugging session:

1. **Boot-time auto-upgrade is now write-aware.** Uncommitted changes only defer the upgrade if they collide with files the upgrade would actually write. Other agents' `workdir/*` runtime state, scratch artifacts, and any other unrelated dirty file no longer block. When the gate does refuse, it names the colliding files and gives the exact command to commit or revert — and special-cases the "previously-deferred stamp on `lore-repo.md`" pattern with tailored guidance.
2. **`/lr:spawn-teammate` Step 7 is now unambiguous.** The skill now explicitly tells the model running it that the current session is the team lead and the operative call is a direct `Agent` invocation — not a delegated subagent prompt or a natural-language directive. The previous wording invited a delegation-to-subagent failure mode that consistently broke first-attempt spawns.
3. **Spawn now verifies the teammate actually started.** A new Step 7c reads `~/.claude/teams/<team>/config.json` after the `Agent` call returns and surfaces silent failures loudly — most importantly the iTerm2 keystroke-corruption race documented as a new Pitfall, where the user's keystrokes during pane-focus shift prefix-corrupt the launch shell command (`pt acd /Users/...` produces `zsh: command not found: pt`, the `&&` short-circuits, the `claude` binary never starts, but `config.json` already lists the teammate as active).
4. **Spawned-teammate input-direction rules are now anchored at boot.** A new `docs/teammate-conventions.md` declares four numbered RULES (interlocutor = user in your own pane; SendMessage is user-directed only; no paraphrase-and-relay; idle pings need no response) as the **single canonical source**. `agent-boot.md` Step 5 detects spawned teammates via `ps -o args= -p $PPID` and loads the conventions doc on every boot — replacing the one-shot spawn-prompt paragraph that empirically washed out after a few turns. The asymmetric two-sided discipline (lead-side redirect + teammate-side rules) is codified in `conventions.md` § Teammate Discipline. The spawn prompt itself carries a one-sentence recap pointing at the boot-time load — *not* a parallel restatement of the RULES, to avoid three-way drift between the spawn prompt, the conventions doc, and the conventions.md summary.

A new convention — **Migration Write Paths** — lets migrations declare their write-set; the boot-time gate uses this for the collision check. Existing migrations 2, 5, and 6 are backfilled.

**Pre-ship code-review followups landed in this same release:**

- **False cross-doc claims removed.** `/lr:check` does not actually flag missing Write Paths sections (this gap is now closed by check #20, see below); `/lr:update` does not share the boot-time gate — by design, the user is interactive there.
- **`/lr:check` #20 added** — three substeps validating each `migrations/<N>.md`: 20.1 section presence (error if heading missing), 20.2 fenced body presence (error if no fenced block), 20.3 body content shape (error if free-form prose appears where globs/sentinel should be). Severity is graduated by blast radius — all three substeps are errors because each fails the gate the same way (gate degrades to blanket-dirty or silently produces an empty write-set). Closes the enforcement gap for the new convention.
- **Precise grep recipe** for the conflict-marker scan in version-check.md Step 1a — anchored line-starts, all-three-markers AND, no false-positive on Markdown setext H1 underlines (`=======`).
- **Unmerged status codes** (`UU`/`AA`/`DD`/`AU`/`UA`/`UD`/`DU`) added explicitly to Step 1a's hard-defer list.
- **Workspace-root path resolution** clarified as a known gap (per-repo `git status` cannot see workspace-root files); migrations 2/5/6 do not declare `.claude/commands/...` because the declaration would be decorative.
- **Step 7c hardened** — skip the lead entry (always has empty `tmuxPaneId`); retry on the Agent-Teams config-write race; do not auto-`SendMessage` ping (would itself violate teammate discipline); prominent guard against `rm -rf` of the team dir blowing away other live teammates.
- **Step 7c failure recovery restructured** — numbered action ladder first, hedging context after.
- **Always-look-at-pane guidance in Step 8** even on verified-live spawns, since Step 7c provably cannot detect the iTerm2 keystroke race.
- **Four numbered RULES collapsed to a single canonical site** (`teammate-conventions.md`); spawn-prompt becomes a one-sentence recap pointing at the boot-time load; conventions § Teammate Discipline becomes a maintainer's index, not a restatement.
- **Migration write-paths parser** in version-check.md Step 1b — body is parsed only inside the first fenced block after the `## Write Paths` heading; prose after the closing fence is ignored. Tolerates the canonical `(none) — <prose>` sentinel form. Migrations 2/5/6 ship with fenced bodies that the parser now correctly reads.
- **Path-quoting consistency** in version-check.md Step 1's `git -C "<lore-agent-repo>"` — survives spaces in the workspace path.
- **Previously-deferred-stamp special case** promoted to an *addendum* that fires whenever `lore-repo.md` is in the colliding set (not only when it is the sole collision); supports YAML quoting variants.
- **teammate-conventions.md banner** corrected to follow the canonical shared-procedure-doc form ("This is a shared procedure doc, not a skill — there is no `/lr:teammate-conventions` slash command").

**Repo migration required:** no — but a cache-clear is required to make the corrected boot-time and spawn-teammate procedures take effect. See **Clear Plugin Cache** below for the mandatory action.

## Clear Plugin Cache

This release **modifies SKILL.md-referenced docs** (`docs/version-check.md`, `docs/spawn-teammate.md`, `docs/conventions.md`, `docs/agent-boot.md`), **adds a new SKILL.md-referenced doc** (`docs/teammate-conventions.md`), and **adds Write Paths to existing migrations** (`migrations/2.md`, `migrations/5.md`, `migrations/6.md`). The plugin cache holds the prior copies, so it must be refreshed before Claude Code will run the corrected procedures. The plugin manifest version also bumps `1.14.0` → `1.15.0`.

After upgrading:

1. `rm -rf ~/.claude/plugins/cache/lore-framework/` (targeted; preserves other plugins' caches), or `rm -rf ~/.claude/plugins/cache/` (broader fallback), or run the workspace's `./clear_plugin_cache.sh` if present.
2. Exit your current Claude Code session and start a new one.
3. Verify: boot any agent — auto-upgrade through v14→v15 should run cleanly even with unrelated dirty `workdir/*` files in the repo. Run `/lr:spawn-teammate <agent>` from a lead session — the first attempt should succeed.

If you skip this step, the v14 copies of `version-check.md` and `spawn-teammate.md` keep loading and the corrected behavior never runs. See `docs/doctor-stale-plugin-cache.md` for diagnosis; if behavior still looks wrong after a clear, run `/lr:doctor`.

## What's Fixed

### Auto-upgrade gate is write-aware (`docs/version-check.md` Step 1)

The previous gate refused on **any** uncommitted change. In practice, lore agent repos routinely carry uncommitted runtime state from other agents — pulse-state files, watch logs, scratch markers in `workdir/` — that has nothing to do with what an upgrade writes. The blanket rule meant the auto-upgrade was deferred almost every boot, and the user had to either commit unrelated noise or stash it just to take a release-notes-only version bump.

The new gate is two-stage:

- **Conflict markers always defer.** A dirty tracked file containing `<<<<<<<` / `=======` / `>>>>>>>` at column 0 is structurally broken regardless of upgrade scope. Always refuse, with a precise file-naming message.
- **Collision check** otherwise. Compute the upgrade's write-set (always `lore-repo.md`, plus the declared `## Write Paths` from each `migrations/<v>.md` for `v` in `R+1..F`). Intersect with the dirty tracked file list. Empty → proceed. Non-empty → defer with the colliding filenames and the exact `git commit` / `git checkout --` commands.

Two specific user-experience improvements:

- **Other agents' workdir state never blocks again.** The motivating instance was an `activities-domain` boot blocked by four `agents/activity-supply-manager/workdir/*.{txt,log,md}` files that had no possible interaction with a release-notes-only v13→v14 bump. With the new gate, those files don't appear in any migration's write-set, the intersection is empty, and the upgrade proceeds.
- **"Previously-deferred stamp" gets tailored guidance.** When the *only* dirty file is `lore-repo.md` and its current `version` is between R and F, that's almost always a partial earlier upgrade. The gate now surfaces this directly: `lore-repo.md is dirty and stamped at version <X> — looks like an earlier auto-upgrade was deferred mid-flight.` plus both the "accept" (`git commit`) and "revert" (`git checkout --`) commands.

Untracked files (`??`) are ignored throughout — the upgrade never writes a path that wasn't already tracked, so untracked files cannot collide.

### Migration Write Paths convention (`docs/conventions.md`)

A new § *Migration Write Paths* requires every `migrations/<N>.md` to declare its write-set under a `## Write Paths` heading — a flat list of repo-relative globs (`agents/*/role.md`, `.claude/commands/lr-*-agent.md`, etc.). The boot-time gate uses this declaration for the collision check.

Migrations without the section fall back to the conservative blanket-dirty rule for the version range that includes them — same friction as today, but only for that specific range, not as the global default. New migrations should always declare their write-set; the existing migrations 2, 5, and 6 are backfilled in this release.

This is the second framework-emitted-shape convention codified after a real-world friction incident (the first was § Tooling: Portable Shell in v14). Same shape: a missing declaration silently degrades a procedure into worse-than-needed behavior; codifying it prevents the regression from recurring.

### `/lr:spawn-teammate` Step 7 — direct `Agent` call (`docs/spawn-teammate.md`)

The previous Step 7 said:

> Compose a single natural-language directive to the lead instructing it to create or extend the Agent Teams team...

Read in context, this was misleading: the skill is *already executing in the lead's own session*. There is no separate "lead" to message. The natural model interpretation — call `Agent` with the directive as the prompt — spawned a subagent that didn't have the `Agent` tool in scope and couldn't actually create the teammate. The result: a half-created `~/.claude/teams/<name>/` directory and a confused user. Real-world usage saw this fail consistently on the first attempt, with the parent session having to intervene manually to call `Agent` directly.

The corrected Step 7:

- States plainly that **the current session IS the lead** and the operative call is a direct `Agent` invocation from this session.
- Resolves a stable team name (`lr-<host-agent-name>-team` or `lr-spawn-team`), pre-creates the team via `TeamCreate` for determinism, and detects-and-cleans stale `~/.claude/teams/<name>/` directories left over from a previous failed spawn.
- Specifies the exact `Agent` parameters: `team_name`, `name` (resolved kebab-case agent name), `subagent_type` (`claude` or `general-purpose` — full-capability), and **`prompt` = the verbatim Step 6 spawn prompt** (the one starting `Read ${CLAUDE_PLUGIN_ROOT}/docs/agent-boot.md and boot as agent...`). The misleading "natural-language directive template" is removed.
- Adds a § Common Pitfalls section documenting the delegation-to-subagent failure mode, the stale-team-directory recovery, and the `subagent_type` requirement so future maintainers don't reintroduce the same ambiguity.

This is an **in-band BETA refinement** in the sense `versioning-release-types.md` describes — `/lr:spawn-teammate` is still BETA, the procedure shifts post-release, and the BETA caveat in `release-notes/10.md` is the contract that licenses the change without an additional VERSION bump dedicated to it. We're shipping it as part of v15 because it travels with the broader procedural-correctness theme of the release.

### Post-spawn verification (`docs/spawn-teammate.md` Step 7c)

The `Agent` call returning is not sufficient evidence the teammate actually booted. Two failure modes leave a teammate registered as `isActive: true` in `~/.claude/teams/<team>/config.json` while no live process exists:

- **iTerm2 keystroke-corruption race** (the input-slip pitfall — see below).
- **Boot failure inside the teammate session** (path wrong, version-check defer, auto-pull error, etc.).

Step 7c reads `config.json` for each newly-spawned teammate, checks `isActive: true` and `tmuxPaneId` non-empty, and on failure surfaces a precise recovery message: open the teammate pane via Shift+Down (in-process) or by clicking into the split pane to inspect, manually run the launch command if the pane sits at a corrupted shell prompt, or remove the stale entry and retry. Verification deliberately does **not** auto-clean `config.json` — that risks racing with a slow-to-start teammate. Surface, don't auto-recover.

Step 8's report now distinguishes verified-live spawns from registered-but-unverified spawns.

### Input-slip corruption Pitfall (`docs/spawn-teammate.md` § Common Pitfalls)

A new Pitfall entry documents the iTerm2 keystroke-corruption failure mode. When Agent Teams' iTerm2 backend opens a new pane and emits the `cd ... && env ... claude --agent-id ...` shell command, the new pane auto-focuses immediately. Keystrokes typed in the original pane during the focus shift leak into the new pane and prefix-corrupt the launch line — the actual `claude` invocation never starts, but `config.json` already records the teammate as active.

The framework explicitly **does not own** the keystroke-emission path — it's Agent Teams' iTerm2 send-text API. Defenses applied in our spawn prompt (Ctrl-U, bracketed paste, etc.) don't reach the corruption site, which is the outer shell line, not the boot prompt payload. The framework's responses are: (1) Step 7c verification converts the silent failure into a loud one; (2) the new Pitfall entry documents the failure mode + suggests upstream filing with Agent Teams (the right defense is a buffer-clearing `\x03\x15` prefix or temp-script wrap on the *launch* command); (3) the user-side mitigation "stop typing for ~1s after invoking the skill" is recorded.

### Spawned-teammate input direction (new `docs/teammate-conventions.md` + `agent-boot.md` Step 5 + § Teammate Discipline)

`/lr:spawn-teammate` exists **for the express purpose of giving the user a parallel pane to work with the spawned agent directly**. Empirically, teammates default to the wrong interlocutor — they SendMessage the lead with status updates, clarification questions, and approval requests instead of talking to the user in their own pane. This forces the lead into a relay role and produces loops.

The prior version included a one-paragraph directive in the spawn prompt addressing this, but the rule washed out after a handful of turns — by the time the teammate is mid-task, it has fallen back to the Agent Teams default of treating the lead as the natural interlocutor.

v15 fixes this in three coordinated places:

- **`docs/teammate-conventions.md` (new)** — declares four numbered RULES freshly on every teammate boot:
  1. **INTERLOCUTOR.** The user in your own pane is your interlocutor. Status, clarifications, approvals, findings, blockers, "I'm done" all go to the user in your pane via your normal text output.
  2. **SENDMESSAGE IS USER-DIRECTED ONLY.** Use SendMessage to the lead/teammates only when the user in your pane has explicitly asked you to share or coordinate.
  3. **NO PARAPHRASE-AND-RELAY.** Don't paraphrase user messages and forward them "for context."
  4. **IDLE NOTIFICATIONS NEED NO RESPONSE.**
- **`docs/agent-boot.md` Step 5 (new)** — every boot now runs `ps -o args= -p $PPID` and checks for `--agent-id` (the canonical marker Agent Teams passes to spawned `claude` instances; `--parent-session-id` is also typically present and is a useful secondary check). If detected, boot loads `teammate-conventions.md` and adopts its standing rules. This survives session length — every boot re-emits the rules from the same source — instead of relying on a one-shot prompt.
- **`docs/conventions.md` § Teammate Discipline (new)** — codifies the asymmetric two-sided discipline. Lead-side: `spawn-teammate.md` § Lead behavior — teammate-to-lead messages (redirect, don't relay or act). Teammate-side: `teammate-conventions.md` (don't message the lead unless explicitly asked). Maintainers touching either side should treat the other side as load-bearing too.

The spawn prompt's own directive paragraph is reduced to a one-sentence recap that points the teammate at the boot-time load (the durable mechanism). The full RULE text lives in exactly one place — `teammate-conventions.md` — so wording changes have a single edit site; agent-boot.md Step 5, the spawn-prompt recap, and the conventions § Teammate Discipline summary are all pointers, not parallel statements.

## What Hasn't Changed

- The boot-time auto-upgrade *control flow* — discover → auto-pull → version-check → read role/lore-context. v15 only refines what the version-check Step 1 gate refuses on; subsequent steps are unchanged.
- All semantics of `/lr:spawn-teammate` outside Step 7 — name resolution, fuzzy matching, context inference, spawn-prompt composition (Step 6), reporting, BETA caveats. The change is to the operative spawn call, not to who is spawned or what their boot prompt says.
- All other skills, descriptors, and lore conventions.
- Migration data for versions 2/5/6 — backfilled with `## Write Paths` headers, but the procedural Steps are byte-identical.

## Impact

- **Boot-time auto-upgrade actually runs in normal use.** The most common shape of an `activities-domain` (or any team-shared) boot — repo with a few `workdir/*` files dirty from another agent's runtime state — no longer defers. The team-shared agent repo is the explicit motivating use case (`team-shared-knowledge-principle.md`).
- **`/lr:spawn-teammate` works on the first attempt.** Previously the parent session had to intervene manually to call `Agent` directly after the skill's first attempt failed inside a subagent. The corrected Step 7 makes this manual workaround unnecessary.
- **Framework authors have a new mandatory section** in every new `migrations/<N>.md`: `## Write Paths`. The cost is mechanical; the benefit is that users with unrelated dirty files don't get blocked from auto-upgrading through the new version.

## Upgrade Checklist

1. **Clear the plugin cache** (mandatory — see Clear Plugin Cache above) and start a fresh Claude Code session so the corrected docs are loaded.
2. Boot an agent in a repo with unrelated dirty tracked files (e.g. another agent's `workdir/*` modifications). Confirm v14→v15 auto-upgrade proceeds cleanly — no spurious deferral on the unrelated changes.
3. Run `/lr:spawn-teammate <agent>` from a lead session. Confirm the first attempt succeeds.
4. *(For framework authors)* When writing the next `migrations/<N>.md`, include a `## Write Paths` section. See `docs/conventions.md` § Migration Write Paths.
