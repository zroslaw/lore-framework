# Migration to Version 25

## Summary

v25 hard-renames two workspace skills and adds the workspace descriptor `lore-workspace.md`:

| Old (v11–v24) | New (v25) |
|---------------|-----------|
| `/lr:workspace-sync` | `/lr:workspace-pull` |
| `/lr:init` | `/lr:workspace-init` |

These are **plugin-side** renames — the skill, script, and doc files live in the `lr` plugin and are
replaced wholesale when the plugin updates (marketplace/plugin refresh, or a `git pull` on a local
checkout, which carries the git renames). **No lore agent repo carries these files**, so there is
nothing to rewrite inside `agents/` or `lore/`, and no generated per-repo artifact references the old
skill names. The only stateful trace of the old names is the **workspace memory file** managed
section (see Step 1), whose refresh is delegated to `/lr:workspace-init` rather than duplicated here.

The repo version stamp (24 → 25) is applied by `/lr:update` / boot auto-upgrade after this migration
succeeds — do **not** stamp it here.

## Scope

Apply per lore agent repo (the standard iteration). Every step is idempotent and writes nothing to
`agents/` or `lore/`; the only real-world artifact is the shared workspace memory file, handled
idempotently by the first repo to reach v25 (subsequent repos find it already refreshed).

## Steps

### Step 1: Refresh the workspace memory file (delegated, idempotent)

The workspace memory file (`CLAUDE.md` on Claude Code, `AGENTS.md` on Codex/Cursor) may carry a
managed section written by the pre-v25 `/lr:init`:

- Legacy markers `<!-- lr:init:start -->` … `<!-- lr:init:end -->` (renamed to `lr:workspace-init:*`
  in v25).
- Payload v1 text that names `/lr:workspace-sync` and `/lr:init`.

Do **not** rewrite the memory file inline in this migration — that logic is owned by
`/lr:workspace-init`, which carries the marker-migration offer, payload v2, and the diff-and-confirm
gate. Instead, **direct the user to run `/lr:workspace-init`** (or `/lr:workspace-init --refresh`)
once, from the workspace root, to migrate the markers and refresh the payload. `/lr:check` #23 also
flags a workspace still on the legacy markers, so this nudge is reinforced by the consistency check.

If no workspace memory file exists, or it has no managed section, there is nothing to do.

### Step 2: Report

Print a one-line summary:

- If a legacy `lr:init` managed section is detected in the workspace memory file:
  `workspace memory file still on legacy /lr:init markers — run /lr:workspace-init to migrate`.
- Otherwise: `no v25 per-repo changes — version stamp only`.

## Write Paths

```
(none)
```

Migration 25 writes nothing to a lore agent repo. Its only real-world effect is the workspace memory
file refresh, which is (a) a workspace-root path the per-repo boot-time collision gate cannot see
(see `conventions.md` § Known gap: workspace-root paths, and the identical rationale in
`migrations/6.md`), and (b) delegated to `/lr:workspace-init` rather than performed here. So a Write
Paths declaration would be decorative — the sentinel is correct.

## Dry-Run Mode

When invoked from `/lr:update --dry-run`, detect the same condition but modify nothing. Report:

- `would advise: run /lr:workspace-init to migrate legacy /lr:init workspace markers` — when a legacy
  managed section is present.
- `no per-repo changes (version stamp only)` — otherwise.

## Notes

- All steps are idempotent — safe to re-run after a partial failure.
- The skill renames are hard renames with no alias; `/lr:workspace-sync` and `/lr:init` stop
  resolving once the plugin updates. See `release-notes/25.md`.
- Do not update `lore-repo.md` frontmatter here; `/lr:update` stamps the version after all migrations
  succeed.
