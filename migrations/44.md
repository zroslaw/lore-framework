# Migration to Version 44

## Summary

Rewrites registered per-agent shortcuts so their boot line names the agent directory **relative to
the workspace root** instead of as an absolute path.

Shortcuts are committed artifacts — `.claude/commands/`, `<workspace>/.codex/skills/`, and
`.cursor/skills/` all travel with the workspace repo. An absolute path in one is true only on the
machine that generated it, so a teammate who clones the workspace receives a shortcut that boots
from a directory they do not have. The same absolute path also made `workspace-status` finding
**S11** report every agent in a cloned workspace as unregistered, because it matches shortcuts by
their embedded target. See `docs/conventions.md` § Committed Artifacts Carry Relative Paths.

All three engines. The invocation is unchanged — the same `/lr-<agent>-agent` command, the same
agent — only the path form inside the file changes.

The migration rewrites existing shortcuts only. It never creates a shortcut for an agent that has
none, and never touches one whose boot line names an agent directory outside the booting repo.

## Scope

Apply to the booting `<lore-agent-repo>`. Only shortcuts whose boot line names an agent directory
under `<lore-agent-repo>/agents/` are candidates.

`<workspace>` is the **workspace root**, not the session working directory. Resolve it: take the
directory holding `lore-workspace.md`, or failing that the parent of `.worktrees/` when the session
sits inside one, or failing that the git toplevel of `<lore-agent-repo>`'s parent. Do not simply use
cwd. A `/lr:update` run from `.worktrees/<repo>/<slug>/` would otherwise find no `.claude/commands/`,
`.codex/skills/`, or `.cursor/skills/` at all, report every agent `skipped`, and let the update
process stamp `lore-repo.md` at 44 — after which this migration never runs again and the absolute
shortcuts stay in git. § Verification cannot catch that, because a later `workspace-status` run from
the real root still matches those untouched absolute paths.

`~/.codex/skills/` is **out of scope**. That location is user-global, so a relative path written
there resolves against whatever workspace happens to be open and would be actively wrong. Migration
37 already relocates those into the workspace; a home shortcut that survives is reported by S15 and
left alone here.

## Steps

All steps are idempotent. Do not stamp `lore-repo.md` in this migration; the update process stamps
it only after every applicable migration succeeds.

### Step 1: Build the owned-agent map

Scan `<lore-agent-repo>/agents/` for directories containing `role.md`. For each, record:

- `<agent-name>` — the directory basename
- `<agent-dir>` — its absolute path, with symlinks resolved
- `<agent-dir-rel>` — `<agent-dir>` relative to `<workspace>`, with a trailing `/`
- `<repo-name>` — the `<lore-agent-repo>` directory basename
- `<agent-purpose>` — the `description` from `<agent-dir>/role.md`'s frontmatter, or
  `(routing description missing — run workspace-init)` when it has none

The last two are needed because Step 3 regenerates whole artifacts: the Cursor and Codex templates
carry frontmatter that substitutes both, and a rewrite that collected only the paths would emit a
literal `<repo-name>` / `<agent-purpose>` or invent one. Migration 33 collects the same fields for
the same reason.

Resolve **both** `<workspace>` and `<agent-dir>` to real paths before computing the relative form.
On macOS `/var` is a symlink to `/private/var`, so a logical subtraction of two paths that were
resolved differently yields a wrong relative path or a spurious `../` prefix.

If `<agent-dir>` does not lie under `<workspace>`, report `skipped` for that agent with the reason,
and leave every shortcut for it untouched. A relative path cannot express a target outside the root
it is relative to, and emitting a `../`-prefixed path would defeat the purpose of the change.

### Step 2: Classify each owned agent's shortcuts

For each owned agent, inspect the three workspace-local locations:

- **claude** — `<workspace>/.claude/commands/lr-<agent-name>-agent.md`
- **codex** — `<workspace>/.codex/skills/lr-<agent-name>-agent/SKILL.md`
- **cursor** — `<workspace>/.cursor/skills/lr-<agent-name>-agent/SKILL.md`

For each that exists, read the boot line and extract its `from` target — the path in backticks
following ``boot as agent `<agent-name>` from ``. Then classify:

1. No file → `absent`. Nothing to do; registration is optional.
2. No boot line, or no extractable `from` target → `unrecognized`. Report and **leave the file
   alone** — an unparseable shortcut is more likely hand-customized than corrupt, and rewriting it
   would discard work this migration cannot read.
3. The target is already relative → `current`. Leave it.
4. The target is absolute and, once resolved, equals this agent's `<agent-dir>` → `rewrite`.
5. The target is absolute and resolves elsewhere → `foreign`. Report and leave it alone: the
   shortcut belongs to a different agent or a different workspace, and the collision rule in
   `register-repo.md` § Collision rule owns that case.

### Step 3: Rewrite

For every shortcut classified `rewrite`, regenerate the whole artifact from the **Registered
shortcut bootstrap** template belonging to **that shortcut's own engine** — the location decides the
template, not the engine running this migration — substituting `<agent-name>` and `<agent-dir-rel>`.
So a `.cursor/skills/` file is rewritten from `docs/engines/cursor.md` even when a Claude Code
session applies the migration.

Step 2 deliberately scans all three locations, so a single session routinely rewrites shortcuts for
engines it is not. The three bootstrap sentences are not interchangeable: they name that engine's own
boot skill (`/lr:boot`, `/lr-boot`, `lr:boot` respectively), and `/lr:check` #18 verifies each file
against its own engine's form. Using the running engine's sentence everywhere produces artifacts this
migration's own § Verification would then fail.

Regenerate rather than string-replacing the path. A shortcut old enough to carry an absolute agent
directory is usually old enough to carry other retired forms — a `plugins/cache/` path, an absolute
`agent-boot.md` path, or a wrapped multi-line bootstrap — and a targeted path substitution silently
preserves all of them. `/lr:check` #18 rejects each of those independently, so a shortcut that is
path-correct and otherwise stale still fails the check.

Emit the bootstrap as **one unwrapped line**. Regenerate the Cursor and Codex frontmatter from their
templates too, substituting `<agent-name>`, `<repo-name>`, and `<agent-purpose>` — "regenerate the
whole artifact" includes the frontmatter block, so do not carry the existing one across. The
regenerated Cursor frontmatter still carries its `paths:` scoping and `disable-model-invocation: true`,
because its template does.

### Step 4: Report

Per agent, per location, report one of `rewritten`, `current`, `absent`, `unrecognized`, `foreign`,
or `skipped`, with the reason for the last three. Report `not applicable` overall when the repo owns
no agents with shortcuts.

A rewritten shortcut is an uncommitted change in the **workspace** repo, not in
`<lore-agent-repo>` — the update process's own commit covers repo-owned paths only. Close the loop
by naming `/lr:workspace-push` in the report whenever at least one shortcut was rewritten, or the
fix stays on one machine, which is the exact failure this migration exists to end.

## Write Paths

```
(none)
```

Like migrations 33 and 37, this migration writes only shortcut artifacts under the workspace root —
`.claude/commands/`, `<workspace>/.codex/skills/`, `<workspace>/.cursor/skills/` — which sit outside
the boot-time repo-relative collision gate. Step 2's ownership classification is the protection for
those paths: an `unrecognized`, `foreign`, or `current` shortcut is never rewritten.

## Verification

After applying, `/lr:workspace-status` should report no new S11 for any agent whose shortcut was
rewritten, and `/lr:check` #18 should flag none of the rewritten files.
